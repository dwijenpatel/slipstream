# slipstream review, 2026-09-04

Scope: the full codebase and README claims, compared against TurboFieldfare
upstream, oMLX, MLX, gpu-kernel, and the NVMAI fork as of 2026-09-03; plus a
review of every TTFT and decode optimization built or measured so far. No
source file in the repo was changed during the review. One throwaway probe
binary was built in the session scratch directory to time prefill chunks.
The README rewrite that followed is commit `1bd6b3e`; the changes this
review proposes as batches 0 and 1 follow it on the same branch.

  tests in 117 suites in 68 s.
- Last commit 2026-08-06, last push 2026-08-11. Four stars, one fork, no

  that lands code there.

## 2. Claims audit

Each item names the README passage and the evidence.

1. **Default slot count is wrong in every table.** Code defaults to 64 slots
   (`RuntimeDefaults.expertCacheSlots`, commit b233c7e, 2026-08-06 21:50).
   The README, last edited 2026-08-06 13:08, labels "16 of 256 (default)" in
   three tables and says "the default 16 slots cap the cache at 1.1 GB".
2. **The per-token budget paragraph mixes before and after.** It gives "6.1 ms
   in full attention" and then says that term was "the first thing rewritten".
   The post-rewrite profile (`profiles/qwen36/README.md`) records 2.4 ms. The
   listed terms sum to 39.2 ms against the stated 40.7 ms.
3. **The 16-to-64 slot gain is quoted from the weaker sweep.** The README's
   "16 percent at a 3k prompt" comes from the sweep whose drift control read
   8.4 percent. The three-pass measurement with a 2.2 percent control reads
   27.76 against 25.12 tok/s, a 10.5 percent gain, and that is the number the
   code comment cites.
4. **Two sentences about oMLX are wrong.** Continuous batching is mlx-lm's
   `BatchGenerator`, which oMLX wraps, not "oMLX's own addition". And a
   single-stream oMLX number would not "land near" mlx-lm: on Qwen3.6-35B-A3B,
   single stream, M3 Ultra, oMLX's Lightning MTP measures 85.2 to 140.4 tok/s
   and its fused gate/up projection measures 104.4 to 115.6 tok/s. No oMLX
   number exists for this model on an M5, and oMLX's Qwen fast paths are
   de-tuned on M5 (prefill floor held at 2048, group-128 native qmm disabled,
   an M5 gather_qmm workaround).
5. **"Near-roofline" needs a stated shape.** gpu-kernel corrected its own
   "80 percent of ceiling" prefill-attention headline to 63.6 and 67.7 percent
   on 2026-08-27 after retiring the full-rectangle denominator. Slipstream's
   "better than 90 percent" figures for decode attention and the head are
   ratios measured on this runtime, but the README does not state the context
   length, and gpu-kernel saw figures above 100 percent when a working set fit
   the system cache.
6. **The KV-resume row is a CLI feature.** `--kv-snapshot` exists only on the
   CLI. The server keeps one in-memory prefix and re-prefills on any
   divergence. The README reads as if resume is general.
7. **Half the docs describe a runtime this repo no longer runs.**
   `docs/SYSTEM_DESIGN.md`, `docs/RUNTIME_CONTROLS.md`, `docs/OPENAI_SERVER.md`,
   and `AGENTS.md` are upstream's Gemma documents: 16 slots, 128-token chunks,
   TurboFieldfare product names, and an instruction not to edit source.
8. **Streaming detokenization is quadratic and can drop text.** `GFDetokenizer.push`
   re-decodes every stable token ID on every push, and when the decoded prefix
   changes it resets and returns an empty delta. Upstream fixed both for Gemma
   (#118, 2026-08) and measured 7.25 ms per token at 16k generated tokens.
   Their fix pins Gemma's decoder and would reject Qwen's `ByteLevel` decoder,
   so slipstream needs its own version. The tokenizer tests only load the
   Gemma tokenizer, so the Qwen streaming path is untested.
9. **Command-buffer failures are printed, not thrown.** Seven sites in
   `RealForwardRunner.swift` do `print("CB error: ...")` and continue.
   Upstream #100 and #159 propagate them with status and label.

## 3. What to pull in

### From TurboFieldfare upstream (cherry-pick, adapt)

- #100 and #159: throw on command-buffer failure with label and status; the
  `AGX_RELAX_CDM_CTXSTORE_TIMEOUT` mitigation for long prefill dispatches;
  fail closed when the tensor-ops pipeline is missing.
- #171: reject unknown request fields with a 400 that names them; accept
  `auto` on the server prefill cap. Server quality for coding agents.
- #118: the incremental, lossless detokenizer design, re-implemented for
  Qwen's `ByteLevel` decoder.
- Open #147: bounded query spans for long-context prefill attention. Needed
  once a tensor-ops kernel runs at hd=256, because the watchdog killed
  eight-row dispatches near 6.8k KV on an M2 Pro.
- Not needed: Gemma image support (#144), app rendering, community reports.

### From oMLX (ideas, not code)

- **Chunk-aligned KV blocks for partial-prefix reuse on a hybrid model.**
  oMLX makes the block boundary equal the prefill forward boundary, stores one
  whole GDN state per boundary in a sidecar, and resumes only at exact
  multiples. Slipstream already chunks prefill and already snapshots whole GDN
  state, so this is the step from one snapshot per conversation to prefix
  reuse across turns.
- **A memory guard.** `proc_pid_rusage` with `ri_phys_footprint` is the number
  jetsam kills on. Slipstream has no memory guard today while the README
  promises a memory budget control. oMLX's admission gate is
  `current + bound(n_tokens) <= 0.90 * cap`, with the bound as the max of an
  analytic estimate and a measured EWMA. Do not raise the wired limit above 95
  percent of RAM.
- **fsync before rename** on snapshot files, and a counter for why a resume
  did not happen.
- **The recurrent-versus-token-local rule.** Any approximation inside a GDN
  layer must stay off the q, k, v rows that feed the recurrence. oMLX found a
  deterministic quality failure at 32k when INT8 touched them.
- **The donor MTP head graft.** oMLX combines a bf16 checkpoint's `mtp.*`
  weights into a quantized checkpoint with tokenizer-hash and geometry checks.
  For slipstream this is the drafting side of speculative decoding.
- **NAX metallib packaging.** Second metallib, SDK 26.2 floor repeated on the
  link step, silent fallback. Slipstream compiles Metal at runtime today.
- Not worth it: ANE prefill offload (private framework classes, plus 4.15 GB
  resident, prefill only); int8 and Hadamard GDN state codecs (oMLX reverted
  to fp32); the gate/up fusion, which slipstream already has by construction
  (one blob per expert, one kernel reading gate and up rows together).

### From gpu-kernel and your MLX branches

- Decode attention: nothing to port. Slipstream's GQA-grouped split-KV kernel
  already runs at about 90 percent; your MLX read-once kernel took MLX from
  57 to 98 percent. Closing 90 to 98 here is worth about 0.5 ms per token.
- Prefill attention at hd=256: the structure, and two rules. A fused kernel on
  the shader ALUs measured 0.37 to 0.46x of the two-matmul fallback on the
  tensor units, so the kernel must run on the tensor-op path. Guards must
  enter through function constants, not runtime branches; a runtime branch
  cost 9 to 11 percent.
- The rows-per-expert law `min(1, R/BM)` as a guard: at chunk 4096, R is 128
  and slipstream is past the knee. At chunk 128 it was 5 percent of ceiling,
  which is the server bug 6ede76c fixed.
- The chunked gated-delta prefill kernel (campaign 4 seed, 1.028x over the
  incumbent, never launched). Its decode value is priced at 1.5 ms per token.
- Small-M quantized matmul (`qmm_t_nax` 32-row block, merged as MLX #4171)
  does not solve the spec-decode verify problem; at t <= 9 batched matmuls
  still cost about t GEMVs. The recorded slipstream pricing says a multi-row
  weights-once int4 GEMV for projections and head crosses break-even alone.

### From NVMAI (upstream PR #105)

- Four of five claims are already present in slipstream or already measured
  and rejected here: parallel pread (present), 64 slots (present) plus mlock
  (rejected, IO-06), RDADVISE default (rejected, RAD-02 and RAD-05), 4096
  chunks (present via `auto`).
- The one new item: phase-one MoE kernel with the activation staged in
  threadgroup memory and 16 rows per threadgroup. They measured phase one at
  56 percent of peak, up from 38, byte-identical, on an M3. Slipstream's DEC-10
  sweep varied row count but never tested staging.
- Their negative results agree with yours: cb merge, spin-wait, prefetch at
  4-bit 35B. They also report layer-major prefill did not pay on their M3
  under `F_NOCACHE`; slipstream's page-cache regime differs.

## 4. TTFT: where the time goes, measured

A throwaway probe timed each 4096-token prefill chunk on the 12k prompt:

| chunk | tokens | keys visible at end | seconds | ms per token |
| --- | --- | --- | --- | --- |
| 1 | 4096 | 4096 | 26.3 | 6.4 |
| 2 | 4096 | 8192 | 42.8 | 10.5 |
| 3 | 3544 | 11736 | 53.3 | 15.0 |

Fit: cost = 4.40 ms per token, plus 985 ns per token-key pair. The fit
predicts chunk 3 at 50.4 s against 53.3 s measured. The token-key term is
attention. At 12k it is 68 s of 122 s. At 24k it is about 280 s of 382 s. At
3k it is about 4 s of 17 s. Attention FLOPs at 12k are 11.3 TFLOP, so the
kernel runs at 0.17 TFLOPS, about one percent of the 15.4 TFLOPS tensor-unit
ceiling.

Cause: Qwen's full-attention layers use `attention_prefill_causal_tiled`. It
assigns one threadgroup per query token per head, loops over every key with
two threadgroup barriers each, and re-reads K and V for each of the 16 query
heads. The tensor-ops kernel exists only for Gemma's 512-wide shape
(`PrefillAttention.swift` checks `headDim == 512`).

Ranked TTFT work:

1. **Tensor-ops prefill attention at hd=256, GQA-shared.** Tile BQ query rows
   by BK keys per KV head with `matmul2d`, online softmax, function-constant
   guards, bounded query spans for the watchdog. Even at 30 percent of the
   tensor ceiling the attention term drops by more than 10x: 12k from 122 s to
   about 60 s, 24k from 382 s to about 110 s, 3k from 17 s to about 14 s.
   Correctness gate: reference-tolerance tests at both production shapes;
   byte identity across kernel paths is not achievable.
2. **Layer-major prefill above 4096 tokens.** Each extra chunk re-streams the
   18 GB expert pool. Worth about 9 s at 12k and 22 s at 24k, nothing at or
   below 4k. Hidden-state buffer about 128 MB at 32k.
3. **Attribute the 4.4 ms per token linear term** with GPU timestamps per
   dispatch before choosing between the chunked GDN kernel, the routed MoE
   tiles, and the projections.
4. **Prefix reuse across turns in the server** (the oMLX block design). For an
   agent loop this removes most prefill from TTFT.

## 5. Decode: the levers that remain

Budget per token at 128 slots, 40.7 ms: 9 ms command-buffer wake, 7.8 ms
expert I/O await, 6.5 ms expert FFN, 6.1 ms GDN, 2.4 ms full attention, 2.4 ms
head, 1.3 ms tail.

1. **Speculative decoding, kernel (a) first.** Multi-row weights-once int4
   GEMV for projections and head. Recorded pricing: crosses break-even alone
   (about 30.7 against 28 tok/s); with the union gather-GEMM for routed
   experts, about 1.6x on code at today's 33.9 percent acceptance. A donor
   MTP head raises acceptance; oMLX measured 83 to 93 percent on Qwen3.6-27B.
   This is the only lever above ten percent.
2. **Phase-one MoE staging** (NVMAI): up to 2.3 ms, about 6 percent.
   Byte-identical, small diff, A/B behind a flag.
3. **GDN decode step** at about 75 percent of ceiling: about 1.5 ms.
4. **Full attention** 90 to 98 percent: about 0.5 ms. Not worth a session.
5. **Floors, measured.** The 9 ms wake cannot be spun away (15 percent slower)
   and MLX avoids it only by keeping routing on the GPU. The I/O await is
   page-cache and SSD copies of 1.77 MB blobs at full rate; only fewer misses
   help, and 64 slots is the measured optimum on this host.

## Addendum 2026-09-05: the GPU clock collapses during expert-read gaps

The uncached I/O baseline (`docs/UNCACHED_BASELINE-2026-09-05.md`) showed
decode kernels taking 28 to 55 ms per token at 16 slots against 13 ms on a
warm 64-slot machine, for identical kernels. The cause is the GPU clock: the
chip lowers it during each layer's 1.5 ms read gap, and the next layer's
kernels run at the low clock. A standalone probe showed the same kernel five
times slower in a command buffer of its own than inside a chain.

Test: a separate process kept one threadgroup of 32 threads looping on the
GPU while the 16-slot uncached decode ran. Five runs, alternated, 3k prompt,
512 tokens, physical reads equal to logical reads in every window:

| Run | Decode tok/s | Kernel time per token | Round trips per token | I/O await per token |
| --- | --- | --- | --- | --- |
| control 1 | 9.71 | 27.6 ms | 15 ms | 59.3 ms |
| heater 1 | 12.61 | 12.8 ms | 7 ms | 58.8 ms |
| control 2 | 9.47 | 29.0 ms | 16 ms | 60.0 ms |
| heater 2 | 12.59 | 12.8 ms | 7 ms | 58.8 ms |
| heater, one threadgroup | 12.65 | 12.7 ms | 7 ms | 58.8 ms |

All five outputs were byte-identical. Prefill was unchanged. Logs and the
heater source: `bench-results/gpu-heater-20260905`.

Landed as the `gpuClockHold` runtime setting (`--gpu-clock-hold`, default
`auto`): `GPUClockHold` keeps the threadgroup queued on a second command
queue while a deadline lies ahead, and every decode step pushes the deadline
out by a quarter second, so the hold covers the token loop of every surface
and ends on its own after the last token. Prefill never touches it. `auto`
stops under macOS Low Power Mode. Energy cost is not yet measured.

Consequence for the ranking: in the small-slot regime, kernel efficiency work
was chasing about 2 ms inside a 28 ms bucket that the clock explains. The
remaining footprint-independent decode term is the SSD itself.

## Addendum 2026-09-05: expert-cache policy, replayed from a routing trace

A cache policy's behavior depends only on the sequence of expert IDs each
layer requests. `TURBO_FIELDFARE_ROUTE_TRACE` now records that sequence,
prefill and decode, and `playbook/route_replay.py` replays it through any
policy at any slot count. Calibration: on a single 3k-prompt run the replay
reproduced the run's own decode miss count exactly at 16 and 64 slots
(86,841 and 35,047); on a ten-request server session it was within 0.2
percent (1,854,319 replayed against 1,850,449 logged), the gap being the
prefill tile order at request boundaries.

The session: a ten-turn coding task through the server (a rate-limited
webhook relay, design note through README), 20,600 traced tokens, 18,772 of
them decode, with the model's reasoning included. Decode misses per token by
policy:

| Slots | LFU (production) | LRU | LFU with aging | Offline optimum |
| --- | --- | --- | --- | --- |
| 16 | 189.3 (40.8% hit) | 183.8 (42.6%) | 175.9 (45.0%) | 135.0 (57.8%) |
| 64 | 98.8 (69.1%) | 77.2 (75.9%) | 73.6 (77.0%) | 39.1 (87.8%) |
| 128 | 39.9 (87.5%) | 27.3 (91.5%) | 25.9 (91.9%) | 11.2 (96.5%) |

On the single 3k prompt the policies tie at 64 slots (78.6 against 79.0
percent). The gap opens over a long session: monotonic LFU keeps use counts
for the life of the process, so experts that were hot in early turns stay
resident after the work moves on. Per-layer slot allocation at a fixed
total, trained on one trace and scored on the other, changed misses by under
0.3 percent in both directions; that idea is closed, as it was on Gemma.

End to end: the same ten user messages replayed against a server started
with `--expert-cache-policy lru`. All ten replies were byte-identical to the
LFU session and the two routing traces were byte-identical. Misses fell
21.7 percent, 1,850,449 to 1,448,727, and every turn improved, 11 to 28
percent. Wall time rose: 849 to 930 seconds, with expert I/O await 376 to
480 seconds. From the first turn, where prefill rates matched, each LFU miss
cost 0.20 to 0.22 ms and each LRU miss 0.32 to 0.34 ms. The host held about
7 GB of file cache. LFU's extra misses are the same mid-frequency experts
over and over, which the page cache serves; LRU keeps those in the slots, so
its remaining misses are the rare experts the page cache does not hold. This
is the mechanism behind CACHE-02's "better miss counts did not reduce the
measured step".

Consequence: on a host whose page cache holds part of the pool, the policies
are complementary and LFU wins on time. In the target scenario every miss is
an SSD read at about 0.36 ms, and a 21.7 percent miss cut at 64 slots is
about 8 ms of a 55 ms token. The default stays LFU until the uncached
harness replays this session under both policies, about 35 minutes per
policy in a quiet window. Both flags are in place: `--expert-cache-policy`
on the CLI and the server.

### Follow-up, same day: `lfu-aging` is the default

Aging replayed as periodic halving of every expert's use count. Periods of
16 to 256 plans and exact sliding windows of 32 to 512 were replayed on both
traces; halving every 32 was best at 16 and 64 slots on both, and unlike LRU
it also improves the single 3k prompt. Decode misses per token:

| Policy | Session, 16 slots | Session, 64 | 3k prompt, 16 | 3k prompt, 64 |
| --- | --- | --- | --- | --- |
| LFU | 189.3 | 98.8 | 169.9 | 68.6 |
| LRU | 183.8 | 77.2 | 169.6 | 67.2 |
| LFU, halving every 32 | 173.9 | 71.8 | 162.2 | 62.4 |
| Offline optimum | 135.0 | 39.1 | 124.6 | 32.0 |

Landed as `ExpertCachePolicy.lfuAging`, the default on every surface, with
`lfu` and `lru` selectable. The runtime under the new default, traced and
replayed, reproduced its own counter exactly: 31,903 misses on the 3k
prompt at 64 slots against 35,047 under LFU, with byte-identical output and
a byte-identical trace.

The decision rests on the target scenario, where every miss is an SSD read
and the miss count is the whole cost. Two measurements are still owed, both
automated with the session scripts and both for the quiet window: the
session replayed under `lfu`, `lru`, and `lfu-aging` on the uncached
harness, which sizes the gain (expected about 8 ms of a 55 ms token at 64
slots), and the same under a warm page cache, which prices what a quiet
machine gives up and belongs in the README beside the decode table.
